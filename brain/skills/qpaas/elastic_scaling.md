# QPaaS 弹性策略创建与下发

记录时间：2026-08-04

适用场景：在 QPaaS 为应用环境创建基于 CPU 的弹性策略，并在不中断现有弹性开关的情况下更新生效策略。

## 前置条件

| 项 | 值 |
|---|---|
| 浏览器启动脚本 | `~/shells/start-ai-chrome.sh` |
| CDP 端口 | `http://127.0.0.1:9222` |
| 自动化方式 | Playwright MCP 连接现有浏览器标签页 |
| 弹性页面 | `http://paas.cloud.qiyi.domain/#/app/appDetail/{appId}/scale` |

启动浏览器：

```bash
~/shells/start-ai-chrome.sh
```

浏览器启动成功时会输出：

```text
DevTools listening on ws://127.0.0.1:9222/devtools/browser/...
```

## 页面结构

应用的「弹性」页面包含两个标签：

| 标签 | 用途 |
|---|---|
| 策略列表 | 创建、查看、编辑和删除弹性策略 |
| 策略配置 | 查看环境当前生效策略；开启、更新、查看或关闭弹性 |

策略列表中的主要字段：

- 策略名称、版本、环境
- 弹性模式
- 部署目标
- 触发类型
- 最小副本数、最大副本数

点击「查看触发类型」可核对指标类型和阈值，例如：

```text
弹性指标类型：CPU
利用率：5
```

## 标准操作流程

```text
核对当前配置 → 参考已有策略 → 创建新策略 → 预览生成配置
→ 更新环境生效策略 → 查看当前配置验收
```

### 1. 核对当前生效状态

进入「策略配置」，选择正确的环境级别（通常为 `PROD`），记录目标环境的：

- 集群弹性开启状态
- 当前生效策略名称及版本
- 操作入口是「更新」还是「开启」

如果弹性已经开启，应使用「更新」切换策略，不需要先关闭再开启。

页面状态应作为权威依据。用户口述的策略名称可能存在拼写错误或已过期，执行前必须以页面实际显示为准。

### 2. 参考已有 CPU 策略

在参考应用的「策略列表」中点击「查看触发类型」，确认 CPU 策略的字段形式：

- 弹性类型选择 `CPU`
- 利用率填写百分比数值，例如 `5`
- 生成的 KEDA 配置中对应：

```yaml
triggers:
  - metadata:
      type: Utilization
      value: "5"
    type: cpu
```

### 3. 创建弹性策略

在「策略列表」点击「创建弹性策略」，填写：

1. 策略名称
2. 策略版本（可选；不填时平台自动生成时间版本）
3. 环境
4. 每个部署目标的弹性模式
5. 最大和最小副本数
6. 弹性触发类型

CPU 固定基数并按指标扩容时，弹性模式选「固定+弹性」。

「单机房最少部署 N 个」表示环境下每个部署目标分别设置最小副本数为 `N`，不是所有部署目标合计为 `N`。

每个部署目标都要单独配置触发类型。只在第一行配置 CPU 不会自动应用到其他机房。

### 4. 提交前核对

提交策略前逐个部署目标核对：

| 检查项 | 要求 |
|---|---|
| 弹性模式 | 固定+弹性 |
| 最小副本数 | 符合单机房最低部署要求 |
| 最大副本数 | 符合扩容上限 |
| 弹性指标类型 | CPU |
| 利用率 | 符合 CPU 阈值 |

策略提交成功后会返回策略列表。先确认新策略出现在列表中，再进行下发。

### 5. 更新生效策略

进入「策略配置」，找到目标环境：

1. 点击「更新」
2. 精确选择新建的策略及版本
3. 选择弹性对象，例如 `Deployment：live-az`
4. 点击「下一步」生成预览
5. 逐个部署目标检查生成的 YAML
6. 进入「配置下发」并点击「确认」

策略下拉中可能同时存在新旧策略，必须按完整策略名和版本选择，避免误选旧策略。

### 6. 验收

下发完成后至少进行两层验收。

第一层，策略配置列表：

- 目标环境仍显示「已开启」
- 当前生效策略名称已变成新策略
- 当前生效策略版本与新建时间一致

第二层，点击「查看配置」，逐个部署目标核对生成的 KEDA `ScaledObject`：

```yaml
spec:
  maxReplicaCount: 48
  minReplicaCount: 8
  pollingInterval: 30
  scaleTargetRef:
    kind: Deployment
    name: live-az
  triggers:
    - metadata:
        type: Utilization
        value: "5"
      type: cpu
```

重点检查 `target-id`，确保每个部署目标都有对应配置，而不是只下发了一个机房。

## 常见踩坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 用户描述的旧策略名与页面不同 | 口述拼写错误或配置已变化 | 以「策略配置」当前生效策略为准，并在结果中说明差异 |
| 只有一个机房显示 CPU 配置 | 每个部署目标的触发类型需要单独添加 | 展开并逐行配置 CPU 与阈值 |
| 最小副本数总量不符合预期 | 把「单机房最少」误解成所有机房合计 | 每个部署目标都填写相同的最低副本数 |
| 更新时仍绑定旧策略 | 下拉列表同时包含新旧版本 | 用完整策略名和版本精确选择 |
| 点击确定后利用率未保存 | CPU 类型选中后未填写必填的利用率 | 检查弹窗中的「请输入利用率」校验提示后再确认 |
| 页面表格中策略名称只显示在第一行 | 同一策略的多部署目标使用合并单元格 | 结合 target-id、Region/AZ 和上下行判断归属 |
| 配置看似成功但参数不确定 | 只看列表，没有检查生成 YAML | 使用「查看配置」逐目标核对 min/max 和 CPU value |
