# Dash 调试知识

- 本地部署点播国际站环境时，`build-nginx-dev.sh xjp master` 会部署 `play-nginx` 的 `xjp` 分支、`luna-rule` 的 `master` 分支，并自动写入 `conf/lua/profile=xjp_hw-qpaas`。
- `subtitle.post_filter` 会影响视频码流，不只是字幕：非多字幕节目（`data.content.isRs ~= 1`）下，如果 `request._ctl_sut_enable` 为 false 且存在 `rp=1` 视频，会执行 `filter_utils.must_no_rate(response, {rp=0})`，只保留 `rp=1` 的视频；如果 `_ctl_sut_enable` 为 true 且存在 `sut=1`，则过滤 `sut=0`。
- `video.group_filter` 会对同一分组内码流按属性优先级去重。默认优先级里 `drmType` 是 `{10,3,5,7,8,9,1}`，所以同 bid/group 下会优先保留 `drmType=5`，清流 `drmType=1` 可能被过滤。
- 大陆站外挂字幕能力依赖 `ft7_stl_main`。4s `feature_config.k_ft7` 里它是第 36 个能力位（bit 35）。`p911/rules/pre/property.lua` 会在 `not request.ft7_stl_main and not request.src_inter and request.pf ~= "22" and request.rs == "1"` 时把 `request.rs` 强制改成 `"0"`，后续 `subtitle.post_filter` 会因 `content.isRs ~= 1` 清空 `program.stl`，表现为不返回外挂字幕。
- tvid `5925298307865400`、src `08023381010000000000` 在旧 `xjp_hw-qpaas` 环境里曾解析为 `pf=nil`，会被 `pre.property` 把 `rs=1` 强制改成 `0`；但在线上大陆站 `bddx-qpaas` 主流程里，4s 配置 `group_5.json` 已把该 src 映射为 `pf=22`，运行时命中 VR 例外，`rs` 保持 `1`。
- 同一请求在 `bddx-qpaas` 运行时走 `mix2_process` 的 `process_name=mainland`。mock boss 通过后，`subtitle.post_filter` 前 `program.stl` 有 3 条，但 `content.isRs=0`，所以规则按非多字幕节目清空 `program.stl`，最终不返回外挂字幕；这不是 `ft7_stl_main=false` 导致的强制硬压字幕。
- `content.isRs` 初始来自 fshark 元数据：`pre/fetch_data_validate.lua` 会把模板默认 `json.data.isRs`（0）写入 `video_data.content.isRs`。后续只有 `subtitle/pre_filter.lua` 在识别为支持多字幕的端时才会置 1。`src=08023381010000000000` 映射 `pf=22` 只能命中 `property.lua` 的 VR 例外，但字幕 `pre_filter` 判断 VR 走硬编码 `vr_srcs/ar_srcs`，该新 src 不在列表里，且 `pf=22` 不在 `is_pc_mobile_tv` 列表里，所以 `isRs` 保持 0。
- 将 `src=08023381010000000000` 加入 `subtitle/pre_filter.lua` 的 `vr_srcs` 后，真实 fshark/boss 链路（仅绕过 vf，未 mock boss）实测 `filter_sut1` 命中 `is_vr=true`，`content.isRs` 被置为 1；但原请求真实 boss 返回 `Q00304 用户未登录` / `st=110`，仍会在 `charge.charge` 阶段提前返回，无法在未鉴权通过的真实请求中看到最终 `program.stl`。
- 快速码流错误 `st=798` 的一条明确路径在 `p911/rules/filter/format.lua`：过滤入口只剩 `fsm=1` 的快速码流，且端能力 `ft5_fast_mp4 ~= true` 时返回 798。码流数量或 `bid=500` 本身不会触发；实测单路普通 500（`fsm=nil`）返回 101，单路 500 模拟 `fsm=1` 后稳定复现 798。常规转码完成、VP 开始返回普通码流后，同一请求可由 798 转为 101。
- H5 的 1080P“露出”和“权益字段”是两条独立链路：`filter/clarity.lua` 的 `h5_1080p_ptid_list` 仅绕过 H5 最高 720P 的过滤；`s/ctype/t` 由 `charge.vip_rate -> p911.vip.dash_ctl` 写入。当前 `vip_rate.lua` 的 `rate_ctl_pfs` 不含 H5 `pf=15`，且 4S `vip_rate_conf` 也没有 `pf=15` 对应模板，因此仅把 src 加进露出白名单会返回 1080P，但 `ctl.v24=nil` 且 1080P 没有 `s`。若要控制非会员试看/不可看，需要同时为 H5 开启码流权益控制并明确映射到权益树（如专门 H5 策略，或经产品确认复用 `phone_conf/default_conf`）。
- `profile` 会改变 fshark 元数据数据源；例如 `prerelease-qpaas` 使用 `vp_conf_qpaas.prerelease`，`bddx-qpaas` 使用 `vp_conf_qpaas.bddx`。若两数据源返回相同码流集合但数组顺序不同，现有 `video_selection.get_selectable_rates_by_prio` 可能产生不同选中结果：默认优先级先按 HDR/DR 圈码流，命中多路同 DR 时不会继续按 code 打破平局，最后 `selected[1]` 直接依赖上游数组顺序。tvid `8830743007564500` 实测 prerelease 的 HDR10 H265(code=1/ts) 在前，bddx 的 HDR10 AV1(code=5/dash) 在前，分别选中不同 vid；`filter.black_white_list` 和后续规则未改变两者相对顺序。
