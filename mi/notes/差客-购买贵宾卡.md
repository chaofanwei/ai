## 进入指定价格详情页

脚本 `chake_buy_vip.py` 现在不再用固定坐标点击“点击购买”。

现在的做法：

- 在贵宾 VIP 卡列表页截屏。
- 用 PaddleOCR 只识别左侧价格区域。
- 找到目标价格数字后，直接点击价格数字中心进入详情页。
- 不再点击“点击购买”，避免 OCR 把相邻商品的“点击购买”识别成目标商品按钮。

OCR 裁剪区域：

```python
OCR_CROP_BOX = (0, 300, 450, 2050)
```

这个区域覆盖左侧价格数字，跳过右侧按钮和大部分无关页面内容。当前实测 `430` 基本够，最后改成 `450` 留一点余量。

当前截图里价格 OCR 框参考：

- `9986`: x 约为 `174..367`
- `29986`: x 约为 `172..410`

列表滚动也不要太大，避免跳过中间商品。现在脚本中 VIP 列表找价格失败后使用约半屏滚动：

```python
down: adb.swipe(520, 1550, 520, 1000, 500)
up:   adb.swipe(520, 1000, 520, 1550, 500)
```

进入详情页后要确认页面显示：

- 标题：`贵宾VIP卡详情`
- 卡类型：`黄金贵宾卡`
- 第一个商品：`梓如商旅金卡（10天）`
- 价格：`￥9986`

## OCR 性能记录

PaddleOCR 整屏识别很慢，之前 `predict` 可能到 `70s+`。

优化后：

- 关闭不必要的文档方向、文档矫正、文本行方向检测。
- 只裁剪左侧价格区域 `(0, 300, 450, 2050)` 做 OCR。
- 因为现在直接点击价格数字，不需要识别右侧“点击购买”。

脚本中的 PaddleOCR 初始化：

```python
PaddleOCR(
    use_doc_orientation_classify=False,
    use_doc_unwarping=False,
    use_textline_orientation=False,
)
```

当前实测：

- 优化前：`predict` 约 `70s+`
- 只做较大区域裁剪时：约 `28.30s`
- 改成左侧价格区域裁剪后：约 `3s+`

脚本每次 OCR 会打印耗时：

```text
ocr timing: screencap=0.35s, crop=0.02s, predict=3.66s, total=4.03s, boxes=14, crop_box=0,300,450,2050
```

字段含义：

- `screencap`: ADB 截图耗时。
- `crop`: PIL 裁剪耗时。
- `predict`: PaddleOCR 推理耗时。
- `total`: OCR 整体耗时。
- `boxes`: 识别出的文本框数量。

只让模型“识别数字”理论上可能有帮助，但 PaddleOCR 常规参数没有简单的“只识别数字”开关。瓶颈主要在文本检测阶段，继续缩小裁剪区域通常比限制字符集更有效。

Mac mini M4 16G 可以跑 PaddleOCR，但不建议轻易做多进程并行 OCR。多个进程可能各自加载模型，内存和调度开销会增加。当前更稳的策略是单实例复用 `_OCR_ENGINE`，加小裁剪区域。

## 收银台与自动支付

进入收银台后，先确认金额正确。

本次 `4万` 示例应显示：

- 总金额：`￥39944.00`
- 应付金额：`￥39944.00`
- 支付方式：`支付宝`

然后按顺序执行：

1. 点击右上角“自动支付”悬浮窗的“启动”按钮。

```bash
/Users/weichaofan/Library/Android/sdk/platform-tools/adb shell input tap 865 553
```

2. 点击页面底部“确认支付”。

```bash
/Users/weichaofan/Library/Android/sdk/platform-tools/adb shell input tap 540 2065
```

触发成功时，悬浮窗会从“启动”变成“停止”，状态类似：

- `状态: 等待按钮(...)`
- `重试: ...次`
- 页面底部“确认支付”按钮会进入倒计时。

此时已进入自动支付流程，可以退出人工操作。
